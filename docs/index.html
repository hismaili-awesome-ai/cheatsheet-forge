The problem

Fluency is not evidence.

A generated cheat sheet reads identically whether or not the commands in it were ever run. There is no visual difference between a command recovered from your terminal history and one assembled from a plausible pattern — same flags, same shape, same confident tone.

Reviewing the text does not resolve this. The reader has no source to check against, so they check the text against their expectations, which is the same thing that produced the text.

The failure is asymmetric, which is what makes it expensive. An invented command announces itself the moment you run it. A dropped command announces nothing at all — the page simply looks complete, and the knowledge you meant to keep is gone.

Both are invisible at review time. That is the property this plugin is built against: not that models are unreliable, but that their output carries no evidence either way.

Mechanism

Three controls. Two of them are not model-mediated.

An instruction is something a model can reason its way around. A PreToolUse hook is a Python process that returns a denial before the tool executes, and no amount of reasoning changes its answer.

Pipeline rule

A citation, or nothing

Every extracted command carries a source_ref naming the dump file and line it came from. The writer emits nothing without one, and a lint step resolves each reference to a real file and a real line before the sheet is written. Invention becomes structurally impossible rather than discouraged.

Pipeline rule

The reviewer re-derives

It reads the raw dumps first and receives no description of what the writer did or intended. It then diffs source against document in both directions, so an omission registers as loudly as an invention. It reports; it never edits.

Tokens, JWTs, private keys, cloud access keys, hardcoded passwords, absolute home paths, private IP ranges and internal cluster DNS. Separately, a command whose binary belongs to another technology cannot land in the wrong sheet. Both checks are deterministic.

Design notes

Why it is built this way.

Each of these was a decision with a cheaper alternative that was tried first and did not hold.

Why hooks instead of stricter instructions

Instructions were the first attempt. They work until the model finds a reading of them that permits what it wanted to do anyway — and a redaction rule that holds ninety-five percent of the time is not a redaction rule, because the five percent is a published credential.

Secrets and topic boundaries are therefore enforced outside the model entirely, by a script that returns a denial the model cannot argue with. Everything a model is genuinely better at — judging whether a destructive command carries an honest warning — stays a judgement.

hooks/hooks.json

Why the reviewer never sees a summary

Handed a tidy account of the source, a reviewing model found one defect in nine. The summary inherits the same blind spots as the document, so the review degrades into checking a text against a paraphrase of itself.

The reviewer now reads the dumps directly, before it opens the sheet, and is told nothing about the preceding stages. It costs more and it is the one place in the pipeline not to economise.

agents/reviewer.md

Why redaction happens at extraction

The analyst is the only agent that reads raw source. Every credential and identifier is resolved there, so nothing downstream ever holds a secret it could leak. Redacting later means every subsequent stage is one mistake away from publishing one.

The names that identify a client or an employer live in a config file inside your repository, never in the plugin — which is precisely why the plugin can be published at all.

agents/analyst.md

Why binary ownership lives in YAML

The boundary check needs to know that oc belongs to OpenShift and gem to Ruby. Encoding that inside the guard would mean editing blocking code every time a technology is added — the worst possible place for routine change.

Ownership is declared in per-technology profiles instead. Adding a stack is one file. A binary owned by two technologies — pod is CocoaPods and also a Ruby gem — simply appears in both, and the guard objects only when the topic is in neither.

tech-profiles/

Why existing files are never overwritten

The writer regenerates sheets wholesale, so the pipeline records a hash of what it last produced. A file that predates the pipeline, or that has been hand-edited since, causes the writer to refuse outright.

The analyst must ingest that file first, absorbing any command not already covered and reporting what cannot be represented — hand-written prose, tables — rather than dropping it silently. A fresh clone reads as untouched and errs toward preserving your work.

scripts/manifest.py

Why the guard is inert in your other repositories

The hook fires on every write in every project once the plugin is installed. It resolves the configured repository root and returns immediately for any path outside it, so an unrelated codebase is never scanned and never blocked.

This is covered by fixtures rather than left to inspection: a guard that quietly governs somebody else's repository is the failure that would make the plugin uninstallable.

Pipeline

Four agents, one gate.

Each stage hands the next a narrower artifact. The reviewer is the only one that returns to the raw source.

01 /analyze analyst · sonnet, high effort

Extracts commands into a structured inventory: deduplicated, parameterised, classified. The only agent that touches unsanitised source.

02 /write writer · sonnet

Composes the sheet from the inventory alone. Never opens a raw dump, and emits no entry lacking a source reference.

03 /review reviewer · opus, high effort

Audits the sheet against the dumps from scratch. Provenance in both directions, destructive-command judgement, upstream accuracy as open questions.

04 /publish publisher · sonnet, high effort

Builds the documentation site and serves a local preview. It has no ability to push, by construction.

▣ human gate

/forge <topic> runs the first three in order and stops, whatever the verdict. A blocked review points back at the writing or the extraction — never at publishing, and never at a way around itself. commands/forge.md

Install

Two commands, then one per repository.

/plugin marketplace add https://github.com/hismaili-awesome-ai/cheatsheet-forge.git
/plugin install cheatsheet-forge@cheatsheet-forge
/cheatsheet-forge:init

Run the first two inside Claude Code from any directory; nothing is cloned by hand. The third runs once in the repository holding your sheets — it infers the layout from what is already on disk, gitignores the raw dumps, and modifies no existing content.

RequiresPython 3.8+ available as python3. PyYAML is used when present; a built-in parser stands in when it is not, because a blocking hook must not depend on a pip install.
ConfigurationSource directory, site directory, file layout and the names the guard treats as identifying all live in a config file that stays in your repository.
Unknown stacksWork with no profile at all. The reviewer locates the official documentation, verifies against it, and reports at reduced confidence with a proposed profile.
